The two skills

A review loop is one review that repeats until no finding is open. A fresh reviewer finds problems, the builder fixes them or proposes a waiver, the tests run again, and a new reviewer checks the result. Two skills cover it.

review-loop

How to run any review that repeats until clean: in the delivery-pipeline workflow, by hand in a conversation, in a release QA pass, or inside a custom Workflow script. It points at the single rules file and doesn't restate the numbers.

Reach for it when a review has to repeat until clean, or someone says "review this and fix what you find." It also covers a loop that stops and asks Keith, and a stopped run that resumes with his rulings.

ui-design-reviewer

The reviewer for screen designs before code exists (mockups, state diagrams, the design decision record), and for built screens compared with the approved mockups. Written from the 22 findings of the WikiMint trial.

Reach for it as the reviewer in the UI design review (Design phase) and the UI review (Verify phase). Use it too when someone asks to check screens, focus order, contrast, or wording on a design.

The mechanism

One round, step by step

Every round runs these checks in this order. The right-hand column shows where a round can leave the loop.

  1. Reviewer

    A fresh reviewer agent reviews the scope. It never built or repaired the work. From round 2 it reports on every earlier finding by id (repaired, still open, or waiver accepted) before it looks for new ones.

  2. Check

    Is a mismatch between a diagram, a Steps: blueprint and the code open (marked needsKeith), with no Keith ruling waiting on it?

    StoppedGoes to Keith. The builder never settles a mismatch alone (CLAUDE.md section 5).
  3. Check

    Is no finding open?

    CleanThe loop ends and lists any waivers for the ledger.
  4. Check

    Is any finding still open after 2 repair rounds?

    StoppedTwo tries is the limit (CLAUDE.md section 18).
  5. Check

    Is this the round cap: round 5, or round 3 for a small item?

    StoppedA medium, high or critical finding is open with no Keith ruling waiting.
    CarriedOnly low findings are open. Each goes to the ledger as an open item for Keith, and the work goes on.
    Go onA Keith ruling is waiting. This repair carries it out and one more review follows.
  6. Builder

    The builder repairs each open finding, proposes a waiver with a written reason, or escalates. It carries out each waiting Keith ruling exactly, in place of the suggested repair.

    StoppedThe builder escalated, or proposed a waiver for a critical or high finding that Keith didn't rule on. The stop comes straight after the repair, so that round's repairs aren't re-tested or reviewed. A resume with Keith's ruling reruns the round.
  7. Re-run

    A fresh agent runs the tests and static analysis again and records exact counts. This happens in the code, security and UI reviews. The UI design review has no tests to run.

Next round: back to step 1 with a new reviewer

A phase can hold more than one review. Verify runs code, then security, then UI. When a loop changes files, every other review in that phase looks again at those files. From the second pass, finding ids carry the pass number, such as code-p2-1, so a ruling always names exactly one finding. If the cross checks haven't settled after 5 passes, the phase stops.

Results

How a loop ends

Clean

No finding is open. The builder repaired each one, or the next reviewer accepted its waiver.

Carried

Round 5 came with only low findings open. They go to the ledger as open items for Keith, and the run goes on. The run doesn't count a carried loop as clean.

Stopped

A stop rule fired. The phase is never marked clean, no later phase runs, and the question goes to Keith.

A stopped run isn't the end. Keith rules on the findings, and the run resumes with his rulings. See When a loop stops.

A small item is one source file under 200 lines, with test files not counted. Keith set the rule on 2026-11-15 (spec 1.2.0), after a test loop on a 40-line function ran 96 minutes with two reviewers a round. For a small item, Verify runs one code-and-security loop, and every Verify loop stops at round 3 instead of 5. The workflow checks the size itself before the Verify reviews. The Design phase isn't sized.

Setup

Before you launch

These come from the WikiMint trial of 2026-11-14.

  • Pick one small item: one function, one screen, or a few files.
  • Settle uncommitted files first, or let the run record them. Discovery lists them in treeAtStart, Build leaves them alone, and they stay out of the commit.
  • Put the stack, how tests run, what done means and the deploy rule in the description. For a Store app the deploy rule is "do not deploy; report devDeployed=false".
  • Pass hasUi, so the UI loops run when they should and stay off when they shouldn't.
  • Pass ledgerPath when one repo holds more than one product.
  • Budget the time. In the trial, a review round took 3 to 9 minutes and a repair round 7 to 16. Discovery, Design and five UI design rounds took 1 hour 52 minutes.
Running it

Three ways to run a loop

In the delivery-pipeline workflow

The workflow runs every loop for you. It refuses to start without project and description. Without stack, its agents ask before assuming PowerShell and Pester.

Workflow({ name: 'delivery-pipeline', args: {
  project: '<product name>',
  path: '<repo folder>',
  description: '<the item, what done means, how tests run, the deploy rule>',
  stack: '<how this repo builds and tests>',
  cloudTarget: 'Azure',
  hasUi: false,
  ledgerPath: '<repo folder>\\Docs\\PIPELINE.md'
} })

Keep the run id and the script path from the launch result. A resume needs both.

By hand, in a conversation

  1. Start each review round as a new subagent (the Agent tool), with the review's checks and the finding shape from the rules file. Don't reuse an agent across rounds.
  2. Act as the builder: repair, or propose a waiver with a written reason.
  3. Run the tests and static analysis for real, and record exact counts.
  4. Give the next reviewer the earlier findings and your repairs.
  5. Apply the stop rules and the cap exactly as written. A loop walked by hand follows the same rules as the workflow.

Inside another Workflow script

The loop code lives only in delivery-pipeline.js. A new script that needs it copies reviewLoop, reviewPhase, loopResult, haltForKeith, the four review schemas, REVIEWS and the limits, then proves the copy against the scenario tests before running it. No standalone review-loop workflow exists yet.

Keith's part

When a loop stops

The run comes back with halted: true and a stop record. The record holds enough to ask Keith without opening the run's journal:

  • each finding behind the stop, with its location, the evidence, the suggested repair, and the builder's action if it escalated;
  • after an escalation, a line saying that round's repairs weren't re-tested or reviewed;
  • the open items the phase agents left for Keith (openForKeith);
  • the low findings carried so far;
  • a resume hint.
  1. Take it to Keith in the question window, one finding per question, with a recommended answer.
  2. Write his answer as a ruling: { id: 'code-3', ruling: '<Keith's words>' }.
  3. Resume with the same args plus keithRulings.
  4. One repair round carries out each ruling, then one more fresh review checks it, past the cap if need be. The loop carries out each ruling once. If its finding is still open after that, the normal rules apply again.
  5. A ruling on a finding that stopped at the 2-repair rule lands on that finding's first repair round in the replay, in place of the original repair. Every agent from there on runs live, and the finding gets one more ordinary repair before the 2-repair rule can stop the loop again.
Workflow({ scriptPath: '<from the launch result>', resumeFromRunId: '<run id>',
  args: { ...the same args..., keithRulings: [{ id: 'code-3', ruling: '...' }] } })
Why only the rulings may change

The Workflow engine caches each agent by its prompt and options. Rulings reach only the repair round that carries them out, so every earlier agent replays from cache. Change the description, or anything else in the args, and every prompt changes: the run starts again from Discovery.

Never resolve a stop yourself, even when the answer looks obvious.

The new reviewer

Using the UI design reviewer

The reviewer reports findings a builder can act on. It doesn't redesign and it doesn't repair, and in a loop it's a fresh agent every round.

Gather before judging

  1. The mockups: the source file (HTML or XAML carries notes and states a PNG hides) and every captured image of a state it comments on.
  2. The design decision record and any state diagram for the screens.
  3. The product's component reference, from the real source: the forge MCP tools for Forge and Confluence apps, the PS7-ISE theme and control styles for DetentShell, the site's own CSS tokens for websites.
  4. Screens Keith has approved and his rulings on this design. Something he ruled out being absent is correct, not a gap.
  5. The product's existing screens, so the new design matches what already ships.

Measure instead of judging by eye

CheckHowWhat it caught in the trial
ContrastSample pixels from the captured image and compute the WCAG ratio. Text needs 4.5:1; large text, input borders and focus rings need 3:1.Input border at 1.3:1
Narrow widthRender a scratch copy of the mockup's markup with headless Edge at the narrowest width the product allows (300px for a Confluence macro column).Cards side by side with no wrap rule
Component propsConfirm every prop the design relies on exists in the component reference.Textfield had no aria-label; SectionMessage had no role
DiagramsRender the state diagram (PlantUML, -failfast2) and match its transitions to the mockup's states.A transition re-entered a state at the wrong substate

The reviewer works in scratch copies and changes no repository file.

The nine areas

Every state drawn

Empty, loading, error, full, and the in-between states users hit.

Trial: "Check again while it runs" was never drawn.

Keyboard and focus

Focus never sits on a disabled control, and survives a component swap.

Trial: Start went disabled while it held focus.

Screen readers

Controls name their state. A live region that exists before the words arrive announces each change.

Watch for: a focus move in the same render can cut an announcement off.

Layout at real sizes

Narrowest and widest widths, both themes, text that wraps instead of clipping.

Trial: cards broke at 300px.

Design tokens

Colors and spacing name the product's tokens, as its shipped screens do.

Trial: the design gave the selected card only as #0C66E4.

Consistency

Field marking, button order and nouns match the screens that ship.

Trial: one form marked optional fields, the other required ones.

Errors users can act on

A field error marks the field, retry advice doesn't loop, long waits say how long.

Trial: "try again in 30 seconds" for a job that runs up to 15 minutes.

Artifacts agree

The decision record, the state diagram and the mockups describe the same behavior.

Trial: one line of counts in the record, three blocks in the mockup.

Plain English

Plain words, no hype, no em dashes in new screen text, Keith's wording kept.

Watch for: one thing called by two names, such as "files" and "programs".

Severity decides what happens at the round cap

SeverityMeansOpen at the cap
CriticalThe builder can't build the design as drawn, or it breaks one of Keith's rulings.Stops
HighA core task fails for a keyboard or screen-reader user, or a state users will hit is missing with no defined behavior.Stops
MediumThe task works but misleads or slows some users: focus in the wrong place, an unannounced change, a layout that breaks at a supported width.Stops
LowPolish and consistency: a token name, a wording mismatch, an edge case with a sensible default.Carried

Grade by what happens to a user, in both directions. Later rounds tend to find small issues in the text the last repair wrote. In the trial, rounds 2 to 5 found 8 new issues, 7 of them low, all in text the previous repair had written.

Reporting a finding

FieldWhat goes in it
idui-design-<n>, or the form the loop prompt gives. Keep ids from earlier rounds.
severitycritical, high, medium or low
whereFile and line, state number, or mockup region
evidenceWhat the reviewer saw, quoted, with the measurement or reference it checked
suggestedRepairOne or two sentences
needsKeithTrue only when the design contradicts something Keith ruled or an approved diagram from an earlier phase. Disagreement between artifacts the builder wrote in this phase is a normal finding.

The reviewer's notes list what it read, what it measured and how, and what it didn't open, so anyone can repeat the checks.

Built screens, in the Verify UI review

  • Capture the app's window, not the whole screen, at a known scale factor.
  • Compare state by state: every approved state has a screenshot, the wording matches the approved text exactly, nothing clips or overlaps, and focus shows where the design put it.
  • A difference from the approved mockup is a finding even when the built version looks fine. Either the build matches the mockup, or the design changes on purpose.
Record keeping

Waivers and the ledger

  • The builder proposes a waiver during a repair round, with a written reason.
  • The next round's fresh reviewer accepts it or rejects it. A rejected waiver leaves the finding open.
  • Agents can't waive a critical or high finding. It goes to Keith instead, unless Keith rules to waive it.
  • Every waiver and every carried finding goes in the project's Docs\PIPELINE.md, or the file named by ledgerPath. The run lists them for Keith at the end.
  • Nothing else goes in the ledger: not a stop, a ruling or a pending resume. Those stay in the stop record and the run's result.

In WikiEngine, WikiMint's ledger is WikiMint\Docs\PIPELINE.md. The root ledger there belongs to the Insights generator.
